# 인수인계 노트

이 노트는 이 작업을 이어받는 에이전트가 이전 대화 없이 시작할 수 있도록, 설계서(메인 탭)에 없는 맥락을 모아 둔 것이다. 설계서가 산출물이고, 이 탭은 사용자의 제약, 확정한 결정, 읽은 것과 못 읽은 것, 작업 규칙을 담는다. 이전 대화의 기억은 다른 대화로 넘어가지 않으므로 이 두 탭이 맥락의 전부다.

## 한눈에

- 프로젝트: 자연어 문진 시스템 전체의 구조 설계. 리포지토리 `Sdabin1209/HealthCheckSchema`는 문진 서비스(런타임)의 데이터 계약만 정의하는 스키마 리포지토리다. 그 위에 문항 저작, 합성 데이터, 모델 개발·평가, 게이트, 운영 관측까지 넓힌 전체 구조를 설계했다.
- 사용자의 목표: 스키마를 세심하게 정의하고, 영역마다 에이전트 하나를 붙여 설계·구현(바이브코딩)시키고, 그것을 합쳐 올린 뒤, 바이브코딩으로 풀기 어려운 파인튜닝(Parser의 LoRA-A, Generator의 LoRA-B)에 집중한다.
- 헤드(최상위)가 정의하는 범위: 영역 사이의 스키마까지. 영역 내부 설계와 구현은 영역 에이전트의 몫이다.
- 현재 단계: 지도, 경계, 결정은 설계서에 정리됐고, 실제 스키마(경계 계약 세트)와 영역 브리프는 아직 없다.

## 사용자의 제약과 선호(대화에서 확인)

- 영역을 마이크로서비스 단위로 만들고 하나로 합쳐 올린다. 운영 환경은 단일 서버다. 합치는 방식은 Compose를 기준으로 하되 Kubernetes로 옮길 가능성도 언급했다.
- 유지보수를 매우 중요하게 본다. 개발 인원과 유지보수 인원이 다르다. 인원 수(5~6명)는 설계 근거로 쓰지 말고 책임 경계가 가장 명확한 구조를 택해야 한다. 인수인계 단위는 리포지토리 하나다.
- Frontend(키오스크 화면)는 다른 팀 담당이다. 우리는 백엔드만 맡는다. 관리자 콘솔 UI는 직접 만들되 나중에 분리할 수 있게 설계한다.
- 운영 형태는 공용 키오스크다. 세션은 한 사람의 한 번의 문진이고, 구체적인 방침은 아직 없다.
- 서버 전체가 멈추면 알림도 위험 감지도 못 하는 것은 수용한다. 현장의 대체 절차는 이 프로젝트의 범위 밖이다.
- 언어는 한국어다. 사용자는 결정을 직접 내리고, 에이전트는 권고한 뒤 확인을 받고 문서에 반영해 왔다.

## 아직 열린 것

- 설계서의 "열린 결정" 표 12개와 각 절 끝의 "미정 사항" 목록이 전부다. 영역 사이 인터페이스에 가장 큰 영향을 주는 것은 저장소의 실제 기술, 비식별 처리의 위치, 모델 평가가 문항 정의를 직접 읽는지, 평가셋 구성이다.
- 공개 API의 전송 방식과 인증, 문진 대상 참조가 무엇인지(환자 번호 등), 허용 중단 시간과 복구 시점, SDK를 만들 언어와 패키지 레지스트리는 정해지지 않았다.
- 신규 계약 10개의 필드는 제안이지 확정이 아니다. 영역별 컴포넌트 설계도 문진 서비스를 빼면 모두 제안이다.

## 리포지토리에서 읽은 것과 못 읽은 것

읽은 것(GitHub 웹 페이지로 확인): README, `docs/architecture.md`, `docs/information.md`, `work/contracts/components.yaml`. 여기서 확인한 사실은 다음과 같다.

- 컴포넌트와 계약: Frontend(FrontendMessage·FrontendInput), Orchestrator(OrchestratorInput·OrchestratorOutput, TurnTrace), Utterance Parser(LoRA-A), Answer Normalizer, Answer Judge, Record Writer, Dialogue Planner, Response Generator(LoRA-B), Staff Console, Result Dispatcher, Question Bank(QuestionBank), Session Store(SessionStore와 저장 포트 요청·결과 계약 4개, 상태는 proposal).
- 모델은 해석과 문장만, 판단은 코드가 한다(역할 분리 원칙). 컴포넌트는 저장소를 직접 읽지 않고 Orchestrator가 읽기·쓰기를 한 곳에서 맡는다.
- 구현은 `generated/schemas/standalone/<계약명>.json`(JSON Schema Draft 2020-12)을 가져가고, `verify.py`가 정적으로 검사한다.
- 저장 결과의 UNKNOWN은 재시도가 안전하다는 뜻이 아니다. 위험(G1)과 직원 요청(F1)은 요구사항 케이스의 이름이다.

못 읽은 것: `docs/versioning.md`와 `work/contracts/proposals.yaml`은 서버 오류(503)로 열지 못했다. `bindings.yaml`, `output_bindings.yaml`, `manifest.yaml`, `work/rules/orchestrator.md`, `work/rules/timing.md`, `docs/validation.md`, `docs/static-integrity.md`, `docs/agent-guide.md`, `AGENTS.md`, `work/schema.md`, `VERIFIED.md`는 시도하지 않았다. 이어받는 에이전트는 계약을 쓰기 전에 `docs/versioning.md`, `bindings.yaml`, `AGENTS.md`부터 읽어야 한다.

## 설계서의 구성

- 개요, 전체 지도, 작업 방식과 스펙 체계, 영역 1~7(각 영역 절 끝에 내부 흐름 그림), 공유 저장소 명세, 영역 간 데이터 교환 명세(E01~E22), 경계 구현과 리포지토리 구조, 배포 구성(단일 서버), 신규 데이터 계약 후보와 버전·계보, 시나리오와 변경 영향, 개인정보·안전·권한, 열린 결정, 가정과 구현 우선순위.
- 표기: 모든 구성 요소에 근거 수준을 붙였다. 확인은 리포지토리에서 직접 확인한 것, 제안은 이 설계의 제안, 미정은 결정이 필요한 것이다.
- 그림 8개(전체 지도 1개, 영역별 내부 흐름 7개)는 위젯이다. 수정 방법은 아래 작업 규칙에 있다.

## 작업 규칙

- 읽지 못한 것을 읽은 것처럼 쓰지 않는다. 리포지토리 근거가 없는 것은 제안으로 표시한다.
- 결정은 권고한 뒤 사용자 확인을 받고 설계서에 반영한다. 사용자는 근거 없는 확신을 싫어하고, 지적이 맞으면 판단을 바꾸는 쪽을 택해 왔다.
- 문서는 Claude Docs 도구로만 고친다. 블록 ID는 읽어서 확인한다. 표의 행을 지우려면 편집 안내를 먼저 읽고, 간단하게는 표 전체를 마크다운으로 다시 보낸다. 임베드의 캡션을 바꾸려면 임베드 블록을 교체한다.
- 그림은 위젯 코드를 한 줄로, 작은따옴표만 써서 쓰고, 글자마다 고유 ID를 붙이며, 색은 토큰만 쓴다. 고칠 때는 `draft-edit`으로 단계 반영한 뒤 `publish`해야 화면에 나온다. 쓴 뒤에는 스크린샷으로 겹침을 확인한다.
- 이전 대화에서 바뀐 판단: 영역별 리포지토리를 처음에는 소규모 팀을 이유로 반대했다가, 인원을 설계 근거로 쓰지 말라는 지적을 받고 책임 경계 기준으로 찬성했다. 게이트 상태 이력의 소유도 게이트 판정 기록으로 일원화했다.

## 다음 작업(제안 순서)

1. 못 읽은 문서를 읽는다. 특히 `docs/versioning.md`, `bindings.yaml`, `AGENTS.md`.
2. 경계 계약 세트를 JSON Schema로 쓴다. 신규 계약 10개, TurnTrace에 릴리스 ID 필드 추가, SDK 인터페이스, 공개 API의 형태. 모든 영역이 의존하는 TurnTrace, ReleaseManifest, GateDecision을 먼저 확정한다.
3. 공통 규약(오류 분류, ID·버전 규칙, 시간·인코딩, 턴 ID 추적, 인증)을 쓴다.
4. 영역 브리프 7개를 쓴다.
5. 모델 영역의 도메인 정의(지표, 통과 임계치, 평가셋 구성, 실패 유형 분류체계)는 사용자와 함께 정한다. 도메인 판단이 필요하고 에이전트가 혼자 채우면 안 된다.
