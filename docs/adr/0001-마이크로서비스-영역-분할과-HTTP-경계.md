# 0001. 영역을 마이크로서비스 단위로 나누고 영역 사이는 HTTP로 만난다

- 상태: 수용(2026-10-28 소급 기록)
- 결정 기록: [D01, D02, D04, D05](../DECISIONS.md), [D06](../DECISIONS.md), [D22](../DECISIONS.md), [D49](../DECISIONS.md), D50
- 관련 ADR: 0002(단일 서버), 0009(에이전트 역할)

## 맥락

사용자는 영역을 마이크로서비스 단위로 만들고 하나로 합쳐 올리길 원했다. 유지보수를 매우 중요하게 보며 개발 인원과 유지보수 인원이 다르다. 인원 수는 근거로 쓰지 말고 책임 경계가 가장 명확한 구조를 택하라고 했다(`HANDOFF.md`). 영역마다 에이전트 하나가 설계·구현한다. 초기에는 영역끼리 SDK(코드)로 의존하는 구조였다(D05).

## 결정

- 영역은 독립 git 리포지토리이고 영역끼리 코드를 가져오지 않는다. 의존할 수 있는 것은 문진 스키마, boundary-contracts, turn-engine, model-runtime, 이웃의 SDK뿐이다.
- 영역 사이의 호출은 HTTP 서비스 API로 한다. 경로와 응답은 `boundary-contracts/HTTP.md`가 정하고, 클라이언트는 `boundary_contracts.clients`가 한 번만 구현하고, 서버는 소유 영역이 구현한다(D49).
- 저장소의 쓰기 권한은 소유 영역 하나에만 있고, 이웃의 저장소 볼륨을 공유하지 않는다(D02, D49, D50).
- 같은 프로세스의 순수 로직은 라이브러리(turn-engine, model-runtime)로 둔다(D06, STRUCTURE 규칙 4).

## 왜

- 책임 경계가 가장 명확하다: 한 사실을 소유하는 영역이 하나이므로 변경 영향 범위를 리포지토리 단위로 말할 수 있고 인수인계도 리포지토리 단위다(HANDOFF).
- 코드 import로 이어 두면 이웃을 배포 단위로 독립시킬 수 없다. D49의 계기는 deploy의 E2E에서 소비 이미지에 이웃 클라이언트를 넣을 방법이 없어 서비스끼리 이어지지 않은 것이다. HTTP는 이미지 경계와 일치한다.
- 클라이언트를 한 곳에서 구현하는 이유: 해시 재검증, tar 안전 처리, 오류 해석이 영역마다 어긋나는 것을 막는다(`boundary-contracts` ADR 0007).
- 순수 로직을 라이브러리로 두는 이유: 턴마다 호출되는 순수 계산에 네트워크를 끼워도 얻는 것이 없다(`turn-engine` ADR 0001).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 모놀리식 한 서비스 | 사용자가 마이크로서비스 단위를 요구했다. 책임 경계와 인수인계 단위가 흐려진다. 직접 비교한 문서는 찾지 못했다 |
| 영역 사이 SDK(코드 import) | D49: 이미지 경계에서 이어지지 않음. 단 읽기 SDK 자체(타입·검증)는 계약 패키지에 남아 있다 |
| 공유 DB로 이웃 데이터 읽기 | D49·D50이 금지. 쓰기 소유 경계가 무너지고 WAL SQLite의 읽기 전용 마운트 문제도 있었다(D50) |
| 메시지 큐/이벤트 버스 | 근거 기록 없음. 영역 사이 자동 연결은 저장소를 보고 일하는 멱등 잡으로 한다(D39). 큐를 비교한 문서는 찾지 못했다 |
| gRPC | 근거 기록 없음. D49는 HTTP로 정했고 gRPC 검토 기록은 찾지 못했다 |

## 결과

- 얻는 것: 영역 단위 독립 개발·시험·배포(이미지 digest, D24), 이웃은 메모리 구현으로 대체.
- 감수하는 것: 영역 개수만큼 서비스와 문서가 늘고 경계 문서의 어긋남이 생긴다(점검에서 반복 발견). 서버 하나가 멈추면 연쇄 영향이 있다(FAULT_MATRIX). 영역 간 호출의 지연·실패 처리가 필요하다.

## 되돌리는 조건

영역을 합치자는 요구(유지보수 인력이 한 팀으로 줄어드는 경우 등)가 생기면 합치는 영역 쌍부터 라이브러리로 내리는 안을 검토한다. 단 쓰기 소유 원칙은 유지한다.
