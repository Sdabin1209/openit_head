# 0002. 한 환경, 단일 서버, Docker Compose를 배포 전제로 한다

- 상태: 수용(일부는 가정이며 사용자 확인 필요)
- 결정 기록: [D10, D11](../DECISIONS.md), [D24](../DECISIONS.md), [D40, D54, D56, D59](../DECISIONS.md)
- 관련 ADR: 0001, 0005

## 맥락

사용자의 제약: 운영 환경은 단일 서버이고 합치는 방식은 Compose를 기준으로 한다. Kubernetes로 옮길 가능성도 언급됐다(`HANDOFF.md`). 서버 전체가 멈추면 알림도 위험 감지도 못 하는 것은 수용한다(D10).

## 결정

- 외부 입구는 gateway 하나이고 서비스는 Docker Compose로 한 서버에 올린다(D11).
- 이미지는 CI가 빌드해 서버 안의 로컬 레지스트리(`registry:2`)에 올리고 digest를 deploy에 제출한다. deploy가 digest 잠금 파일로 코드 축을 고정한다(D24, D07). 외부 레지스트리와 쿠버네티스는 쓰지 않는다.
- 서빙·백 서버는 RTX 4090 24GB 1장, 학습 서버는 A6000 48GB로 다르다고 가정한다(D54, D59에서 사용자 확인됨). `gpu-dev`는 개발 전용이다.
- 고가용성·대기 서버·상시 대응은 범위 밖이다(D10, D56). 자동 백업과 복구 스크립트는 deploy에 이미 있는 선택 기능으로 낮췄다(D59).

## 왜

- 사용자의 명시 제약이다. 근거는 사용자 요구이며 이 팀이 비교 측정한 것이 아니다.
- 단일 서버 전제를 두면 분산 합의, 서비스 메시, 다중 노드 스토리지 같은 복잡도를 설계에서 뺄 수 있다. 헤드는 이를 범위로 받아들였다(D10).
- digest 고정 방식은 쿠버네티스로 옮길 때 그대로 이식된다(D24). 쿠버네티스를 지금 쓰지 않는 이유가 이식 가능성이 이미 확보됐기 때문이다.
- 한 환경 전제의 한계: 개발자는 컨테이너 밖(가상환경)에서 개발하고, 컨테이너는 매 변경마다 확인하는 산출물이다(D22). 이는 "내 환경에서만 돈다"를 막기 위해 두 번째 환경 검증(사용자 피드백)과 함께 쓴다.

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| Kubernetes | 근거 기록: 사용자가 가능성만 언급했고 D24가 "필요해지면 이식"으로 미뤘다. 지금 필요하다는 근거가 없고 운영 부담이 크다는 비교 측정은 없다 |
| 다중 서버 / 고가용성 | D10이 비보증으로 명시. 사용자 수용 |
| 외부 레지스트리 | D24: 서버 안의 로컬 레지스트리로 충분하다고 정함. 외부 서비스 의존과 인증 비용 비교는 기록 없음 |
| 컨테이너 안에서 개발 | D22: 택하지 않았다고 명시. 이유 문장은 "개발은 컨테이너 밖, 컨테이너는 산출물"이 전부 |

## 결과

- 얻는 것: 구성이 단순하다. 로컬에서 같은 Compose로 재현 가능하다.
- 감수하는 것: 서버 중단 시 서비스·알림이 멈춘다(D10, 외부 감시로 담당자에게 알림). 24GB 실측은 아직 없다(OPEN_GAPS U02, H1). 서버 토폴로지는 가정이다.

## 되돌리는 조건

사용자가 가용성 요구를 확정하거나 병원 규모가 단일 서버를 넘으면 오케스트레이터 이전을 검토한다. 이때 digest 잠금과 서비스별 헬스 엔드포인트가 이식 기반이다.
