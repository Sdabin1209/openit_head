# 0003. 두 모델 구조: LoRA-A(추출)와 LoRA-B(응답), 서비스에는 규칙 코드를 두지 않는다

- 상태: 수용(구조 방향. 일부 세부는 미확정)
- 결정 기록: [D74](../DECISIONS.md), [D75](../DECISIONS.md), [D76](../DECISIONS.md), [D77](../DECISIONS.md), D78, D81
- 관련 ADR: 0004, `turn-engine` ADR 0005, `boundary-contracts` ADR 0008

## 맥락

초기 설계(v1)는 파서(LoRA)→정규화기→판정기→기록기→Plan 코드→생성기(LoRA)였다. 학습 데이터셋 v2(IO_SPEC v2, 2026-10-13 확정)는 한 모델이 정규화·절차·다음 문항까지 낸다. LoRA의 입출력 형식은 우리가 바꿀 수 없는 고정 입력이었다(D74).

## 결정

- LoRA-A: 환자 발화에서 값을 추출하고 정규화하며 절차(`action`)와 다음 문항(`next_item`)을 한 번에 낸다(`ActionExtraction`). LoRA-B: 응답 문장을 만든다(`ResponseText`). 시작(START)은 A를 부르지 않고 B만 부른다.
- 서비스에는 정규화기·판정기·Plan 코드를 두지 않는다. 서비스가 하는 일은 문항 번호로 질문 문장을 찾는 표 찾기, 저장·전달, 안전장치뿐이다(D74).
- 서빙의 모델 입력 글자는 학습 데이터와 글자 단위로 같아야 한다. 서빙이 학습에 맞추고(`prompt-4`), 학습기를 서빙에 맞추지 않는다(D77).
- 기반 모델은 프로파일로 고른다(어댑터 교체는 model-serving만 바꾼다, D72). 학습 정본은 학습 서버의 코드다(D78).
- 문항 순서·건너뛰기 표는 survey-service가 소유한다(D76).

## 왜

- 학습 데이터셋이 이미 v2 형식으로 확정됐고 형식은 바꿀 수 없다. 구조를 데이터에 맞춘다(D74, 사용자 결정).
- 근거(D74): v1은 가능한 상황을 코드로 다 만들어야 해서 경우의 수 대응이 문제였다. 모델이 일반화로 풀고 서비스는 안전장치에 집중하는 편이 유지 가능하다.
- LoRA는 학습된 입력 글자에서만 의도한 대로 동작한다. 학습 서버 val(A 400행, B 300행)에서 확인한 직렬화 규칙에 서빙이 맞춘다(D77). 이미 학습된 어댑터가 있어 학습기를 바꾸지 않는다.
- 같은 기반 모델에 두 어댑터를 올려도 VRAM 증가가 약 0.07GiB로 작았다(D48, gpu-dev 측정). 두 모델 구조의 비용이 작다는 근거다.
- 문진 스키마·표의 소유를 survey-service에 두는 것은 D19, D21, D76이다(스키마 소유 영역이 표를 만든다).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| v1 유지(규칙 코드 + 두 LoRA) | 학습 데이터가 v2 형식이다. 이중 구현이 된다. D74 근거 |
| 한 모델로 추출과 응답을 모두 | 근거 기록 없음. 학습 데이터셋이 A/B 둘로 나뉘어 있어 그에 맞춘 것이다. 단일 모델 안은 비교한 문서를 찾지 못했다 |
| 서빙이 학습 직렬화에 맞추지 않고 JCS 사용 | D77: 어긋나면 학습된 동작이 나오지 않는다. 확인된 불일치(prompt-3) |
| 학습기를 서빙에 맞춤 | 이미 학습된 어댑터가 있다 |

## 결과

- 얻는 것: 서비스 코드가 줄고 규칙은 데이터로 바뀐다(모델의 시행착오는 설정으로 반복, D39).
- 감수하는 것: 모델이 틀릴 수 있다. 그래서 사후 검증이 필수다(ADR 0004). 학습 파이프라인은 비전문가에게 어렵다(D78, 이후 수정 필요). 24GB 이상의 실제 모델은 아직 실측하지 못했다(H1). 위험 신호 입력원 등 일부는 미확정이다(D76(3), D79).

## 되돌리는 조건

데이터셋 형식이 다시 바뀌면(v3) 같은 방식으로 구조를 맞춘다. 모델이 목표 정확도를 못 내면 규칙 코드를 부분적으로 되돌리는 대신 데이터·학습을 먼저 고치는 것이 D38의 방향이다.
