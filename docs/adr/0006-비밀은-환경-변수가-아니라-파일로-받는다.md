# 0006. 비밀은 환경 변수가 아니라 파일로 받는다

- 상태: 수용(D84). 운영 비밀 정책(발급·회전·보관)은 미정
- 결정 기록: [D84](../DECISIONS.md), [D88](../DECISIONS.md)(U7·U8 인증), [D85](../DECISIONS.md)
- 상세 ADR: `boundary-contracts/docs/adr/0009-비밀은-read_secret으로-파일에서-읽는다.md`

## 맥락

2026-10-27 gpu-dev 측정 에이전트가 `docker exec ... env`로 시험용 토큰 5개를 출력에 노출했다. 근본 원인은 구조였다. 모든 서비스가 `env_file`로 토큰을 환경 변수로 받아, 컨테이너 접근자라면 누구나 `env`/`inspect`로 평문을 읽을 수 있었다.

## 결정

- 서비스는 `<이름>_FILE`로 받은 경로의 파일을 읽는다. 환경 변수 `<이름>`은 개발·시험용 호환일 뿐이다.
- 읽는 코드는 `boundary_contracts.read_secret(NAME)` 하나다.
- deploy는 compose `secrets:`로 `/run/secrets/...`에 마운트한다.
- 비밀 값은 이미지, 리포지토리, 설정 파일, 로그, `/readyz`, 오류 응답에 넣지 않는다. 에이전트 브리프에도 환경·토큰 출력 금지를 명시한다.

## 왜

- 사용자가 증상(노출된 토큰 교체)이 아니라 근본 원인을 고치라고 지시했다(D84).
- 환경 변수는 `env`, `inspect`, 프로세스 상속, 크래시 덤프로 새기 쉽고, 파일은 권한과 마운트 범위로 제한할 수 있다.
- 한 구현을 공유 패키지에 두면 영역별로 같은 실수를 반복하지 않는다(`boundary-contracts` CHANGELOG 2.0.2).
- 기기별·사람별 인증과 같은 선상의 결정: 토큰이 곧 자격이므로 노출 비용이 크다(D88 U7, U8).

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 환경 변수 + 출력 금지 지침 | 구조가 같아 다시 노출된다 |
| 외부 비밀 관리자(Vault 등) | 근거 기록 없음. 운영 정책(D-A)이 미정이고 단일 서버에 서버를 추가하는 비용은 비교한 기록이 없다 |
| 이미지·설정 파일에 포함 | 이미지·리포 노출. 워크스페이스 규칙으로 금지 |

## 결과

- 얻는 것: `env`로 토큰이 보이지 않는다. 시험·점검에서 비밀 출력 점검(OPEN_GAPS U07·U08 데모 비밀 점검 통과)이 있다.
- 감수하는 것: 발급·회전·보관 정책(D-A)은 열려 있다. 파일 권한/마운트의 실제 설정은 deploy 소관이며 헤드가 직접 확인하지 못했다.

## 되돌리는 조건

외부 비밀 관리자를 도입하면 `read_secret`의 원천만 바꾼다.
