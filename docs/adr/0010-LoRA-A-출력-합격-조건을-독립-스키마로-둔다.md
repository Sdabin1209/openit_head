# 0010. LoRA-A 출력의 합격 조건을 독립된 스키마로 두고 turn-engine 리포를 없앤다

- 상태: **수용(사용자 확정, 2026-10-28, D104)**. 규칙 명세는 **정형화된 데이터**다(사용자 지정). 이전 순서는 전수 점검 결과를 보고 확정한다.
- 관련: 프로젝트 구조 규칙 6개(영역·컴포넌트는 서로의 구조를 모르고 스키마로만 만난다. 영역 안 스키마는 영역, 영역 간 스키마는 헤드), ADR 0001, ADR 0003, `turn-engine` ADR(소멸 대상), `model-runtime` ADR 0003

## 맥락

- turn-engine(코드 약 200줄)은 LoRA-A 출력(`ActionExtraction`)이 규칙에 맞는지 보는 순수 함수와 문항 순서표(`QuestionFlowTable`)로 이루어져 있다. 하는 일은 "LoRA-A 출력의 합격 판정" 하나다.
- 이것을 survey-service(9개 파일), model-lab(7개), synthetic-data, model-runtime, deploy가 코드로 import한다. 한 영역이 다른 영역의 구조(함수, 표 형식)에 기대는 것이다.
- 재시도 로직이 둘로 중복된다: model-runtime의 `ModelSession`이 형식 검증·재시도를 하고, survey-service가 의미 검증 위반 시 같은 요청을 한 번 더 보낸다(D75).
- 계약이 PATCH 한 번 바뀔 때마다 turn-engine 재릴리스와 약 12개 리포의 핀 교체가 필요했다(2026-10-28에 두 번).
- 문항 순서표 형식은 계약에 없고 turn-engine이 임시로 정했다(`flow.py` 머리 주석).

## 결정

1. **독립 스키마로 올린다.** (헤드 소유, `boundary-contracts`)
   - 이미 있는 `ActionExtractionInput`, `ActionExtraction`.
   - **`QuestionFlow`** 스키마(문항 순서와 건너뛰기 규칙). 문진 스키마의 `question_flow.json`에서 survey-service가 만들어 넘기는 값의 형식이다.
   - **`ActionExtraction` 합격 조건**: 스키마로 표현되는 부분은 스키마에, 표현되지 않는 부분(`targets`⊂`values` 키, `next_item`이 순서표로 계산한 값과 같음)은 **규칙 명세(데이터)**로 적는다. 명세는 스키마와 같은 버전으로 움직인다.
   - **기준 검사기**: 명세를 읽어 판정하는 참조 구현을 계약 패키지의 `conformance`에 둔다. 영역들의 보장을 시험하는 정본이다.
2. **LoRA-A 컴포넌트(model-runtime)가 보장한다.** 출력이 위 스키마와 합격 조건을 만족함을 자기 안에서 보장한다(생성 → 스키마·의미 검증 → 재시도는 컴포넌트 안). 호출자에게는 합격한 출력만 나간다.
3. **읽는 쪽은 믿고 쓴다.** LoRA-A 컴포넌트가 직접 판정할지 모델 출력을 믿을지는 컴포넌트가 정한다(사용자 지정). 어느 쪽이든 내보낸 값은 스키마를 만족한다고 보증하고, 다른 컴포넌트는 재검증·재시도를 하지 않는다.
   **읽는 쪽은 참조만 한다.** survey-service는 검증·재시도를 하지 않고, 합격한 `ActionExtraction`을 스키마대로 읽는다. model-lab·synthetic-data는 평가·데이터 점검에 기준 검사기를 읽기 전용 참조 도구로 쓴다.
4. **turn-engine 리포를 폐지한다.** 코드는 기준 검사기로 계약 패키지에 흡수된다. 버전 열차에서 turn-engine 단계가 빠진다. 폐지 전 이전 순서는 아래 결과에 둔다.
5. **I9 `extract` 요청에 `QuestionFlow`를 싣는다.** LoRA-A의 학습된 입력 글자는 바꿀 수 없으므로(D77) 모델 입력과 별개로, 컴포넌트 입력에 순서표를 더한다. 이 변경은 영역 간 스키마 변경이라 헤드 책임이다.

## 왜

- 규칙 1~6: 합격 조건은 LoRA-A 출력 스키마의 일부이므로 영역도 컴포넌트도 아니고 스키마다. 스키마를 헤드가 정하고, 보장은 컴포넌트가 하고, 읽는 쪽은 참조한다.
- 재시도 중복을 없앤다. 검증과 재시도가 보장하는 컴포넌트 안에 한 곳으로 모인다.
- 버전 결합을 줄인다. 스키마와 합격 조건이 한 버전으로 움직이고 별도 라이브러리의 열차가 없어진다.
- 근거 수준: 위 맥락의 수치(파일 수, 재릴리스 횟수)는 코드와 오늘 작업에서 센 값이다. 이 구조가 지연이나 운영에 주는 영향은 **측정하지 않았다**.

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| turn-engine을 survey-service의 컴포넌트로 흡수 | 사용자 지적: 이 로직은 LoRA-A 출력의 합격 조건이라 survey-service만의 것이 아니다. model-lab·synthetic-data도 같은 판정이 필요하다 |
| turn-engine을 영역으로 두고 HTTP 서비스화 | 순수 계산에 네트워크를 끼워도 얻는 것이 없다(ADR 0001). 서비스가 하나 늘어난다 |
| 현행 유지(라이브러리 리포) | 영역이 이웃의 코드 구조에 기대고 재시도가 중복되며 버전 열차 비용이 계속된다 |
| 합격 조건을 순수 JSON Schema로만 표현 | 순서표 계산과 집합 조건은 표현할 수 없다. 명세+기준 검사기가 필요하다 |

## 결과

- 얻는 것: 합격 조건의 정본이 하나(스키마 묶음), 검증·재시도가 컴포넌트 안으로, 열차 단순화.
- 감수하는 것: 계약 패키지가 규칙 명세와 기준 검사기를 갖게 되어 커진다. I9 요청 스키마가 바뀌어 survey-service·model-runtime·release-gate 등이 함께 움직인다. 규칙 명세는 데이터로 확정(사용자 지정)했다. 데이터의 구체 형식(필드, 표현)은 전수 점검 뒤 정한다.
- 이전 순서(제안): (1) `QuestionFlow` 스키마와 명세 초안을 계약에 추가하고 기준 검사기가 현재 turn-engine과 같은 판정을 하는지 같은 입력으로 대조 시험(대조는 일시적 도구이며 정본 아님), (2) model-runtime에서 LoRA-A 컴포넌트가 검사기로 보장하게 함, (3) survey-service의 검증·재시도 노드와 import 제거, (4) model-lab·synthetic-data의 import를 기준 검사기로 교체, (5) turn-engine 리포 폐기(태그는 지우지 않는다).

## 되돌리는 조건

기준 검사기를 계약 패키지에 두는 비용이 커서 계약 버전 변경이 잦아지면 합격 조건 검사기만 별도 패키지로 분리하는 안을 새 ADR로 비교한다.
