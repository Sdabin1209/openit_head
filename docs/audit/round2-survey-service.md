## M1. prescreen이 세션 존재·상태 확인보다 앞이라 없는 세션 ID로 허위 알림이 나가고 응답이 COMMITTED로 나온다 [M, 확인]

- 근거: `graph.py` build()의 `START -> prescreen -> load_session`. prescreen은 세션을 읽지 않고 `staff_console.deliver`부터 한다.
- 재현(Rig, 임시 스크립트): 존재하지 않는 sid="NOPE"에 "가슴이 아파요" 발화 → 알림 1건 생성, 응답 `response_text="바로 직원을 불렀습니다..."`, `turn_failure_signal={"session_id":"NOPE","write_committed":"COMMITTED","staff_alert":"DELIVERED"}`. 아무것도 확정하지 않았는데 COMMITTED로 나온다. (정상 경로의 세션 없음 응답은 404/오류이므로 계약과 동작이 갈린다. 계약 PUBLIC_API.md 오류 404(세션 없음).)
- 영향: 키오스크 토큰(또는 기기 토큰)을 가진 쪽이 임의 세션 ID로 직원 알림을 만들 수 있다(목록에 세션이 없는 알림, 직원이 열면 404). 기기별 토큰의 소유 검사도 세션 메타가 없으면 통과(`_device_denied`가 owner None이면 허용)한다. 끝난 세션·정지 중 세션에서도 알림이 나간다(정지 중 반복 발화는 ADR-0013이 감수로 적었지만 없는 세션은 적지 않음).
- 제안 수정: prescreen 알림을 세션이 존재하고 위험 정지할 수 있는 상태일 때만 보내거나(DB 읽기 실패는 알림 우선이므로 예외로 두고), 없는 세션이면 알림 대신 정상 404 경로로 보낸다. 최소한 `write_committed`를 실제 확정 여부로 맞춘다.
- 자율 수정 가능: 예.

## M3. check_values가 실제 문항 세트의 선택지·단위 정의로 검증되지 않았다 [M, 추정]

- 근거: `extraction.py` `check_values`의 `choices`/`yes_no_map`/`units` 규칙(VALUE_TYPE_MISMATCH). `scripts/reference_agreement.py` 문서: 대조는 이 영역 시험용 세트(선택지·단위 정의 없음)로만 했다. 즉 가장 엄격한 규칙(선택지 칸에 선택지 밖 값, 단위 목록 밖 단위)은 학습 데이터 정답과 한 번도 대조되지 않았다.
- 영향: 실제 문항 세트에서 모델이 라벨 대신 id를 쓰거나 단위 표기(`kg`/`킬로`)가 다르면 정상 답이 거부되어 같은 요청 1회 재시도 후 NOT_COMMITTED가 된다. 환자는 같은 말을 반복하고, 반복이 REASK 상한과 만나 직원 호출로 올라갈 수 있다. 확인한 것은 코드 경로뿐이고 실제 세트로 돌려 보지는 못했다.
- 추가: `nxt == "END"`이면 span이 현재~마지막 문항 전체가 되어 "현재 문항 밖 저장 금지" 규칙이 사실상 풀린다(모델이 END를 내면 건너뛰기 규칙으로 건너뛸 문항의 칸도 저장 가능). 의도(운동 문항 3개 일괄)보다 넓다. 확인한 것은 코드 읽기까지.
- 제안 수정: 실제 문항 세트(릴리스 번들)로 reference_agreement를 돌려 거부율을 측정, 결과가 0에 가깝지 않으면 규칙을 경고 수준(카운터만)으로 낮춘다. END일 때 span은 flow의 건너뛰기 표를 적용한다.
- 자율 수정 가능: 예(측정은 데이터 접근이 필요).

## M4. 기기별 토큰이 계약 F와 맞물리지 않을 수 있다 [M, 추정]

- 근거: PUBLIC_API.md F절: 게이트웨이가 기기 토큰을 확인하고 "서비스 호출에는 서비스 키오스크 토큰을 붙인다". 서비스는 이제 기기별 토큰 표로 세션 소유를 검사한다(`api.py` `_device_denied`). 게이트웨이가 공유 토큰 하나로 서비스를 부르면 `_tl.device`가 항상 None이라 세션의 `device_id`가 전부 NULL이 되어 소유 검사가 작동하지 않는다. 게이트웨이를 읽지 못해 어느 쪽이 맞는지는 확인하지 못했다.
- 부수 확인(코드): 소유 검사는 `owner is not None`일 때만 막으므로 공유 토큰으로 만든 세션·이전 세션은 누구나 접근한다. 기기 토큰 표를 켠 상태에서 공유 토큰은 기기 소유 세션에 접근 못 하지만(404) 소유 없는 세션과 신규 세션 생성은 가능하다. `/readyz.kiosk_tokens.warning`이 이를 알린다.
- 제안 수정: 헤드가 F절을 "게이트웨이는 기기 토큰을 서비스까지 전달" 또는 "서비스는 `X-Device-Id` 헤더를 신뢰"로 정리한다. 변경 요청 문서화 필요.
- 자율 수정 가능: 아니오(계약 변경, 헤드).

## L (낮음)

- L1 `_has_surrogate` 재귀 깊이 [확인]: 중첩 깊이 약 500 이상의 JSON 본문(인증된 요청)에서 `RecursionError`. `json.loads`는 3000 깊이도 통과한다. `PublicApi.handle`에 예외 처리가 없어 요청 스레드가 예외로 끝나고 연결이 비정상 종료될 것으로 추정(핸들러 경유 동작은 직접 확인하지 못함). 제안: 반복문(스택)으로 바꾸거나 `RecursionError`를 400으로 처리. 자율 수정 가능.
- L2 SSRF: NAT64 접두 `64:ff9b::/96`이 `is_global`이라 `https://[64:ff9b::7f00:1]/`·`[64:ff9b::a9fe:a9fe]`(메타데이터 주소 임베드)가 문법·해석 검사를 통과(`host_is_public` True 확인). NAT64 게이트웨이가 있는 망에서만 의미가 있다. 등록 문법 검사에서 `127.1`, `0x7f.0.0.1`, `*.localhost`는 통과하지만 보낼 때 해석 검사로 막힌다(확인: False). 제안: 64:ff9b::/96와 2002::/16(6to4)도 임베디드 IPv4를 꺼내 검사. 자율 수정 가능. (DNS 재바인딩 한계는 문서에 이미 명시됨.) 추가로 DNS 해석(`getaddrinfo`)에 시간 상한이 없어, 느린 DNS가 prescreen 알림 전달 경로(턴 스레드)를 붙잡을 수 있다(추정).
- L3 /readyz 정보 노출(인증 없음) [코드 읽기]: 위험 규칙 id별 적중 횟수(`hits_by_rule`, 자해 규칙 포함), 규칙 파일 sha256, 보존 기간, 공유 토큰 사용 여부와 기기 토큰 수가 노출된다. 시크릿 값은 아니지만 인증 없는 엔드포인트에 임상적 집계와 인증 구성이 실린다. 제안: 상세는 인증 뒤로, /readyz는 요약만. 자율 수정 가능(계약 /readyz 형태 확인 필요).
- L4 `X-Openit-User` [코드 읽기]: 서비스는 형식(`USER_ID`)만 보고 모든 역할의 접근 기록에 쓴다. 게이트웨이가 헤더를 지운다는 전제이며, 서비스 포트(0.0.0.0)에 직접 닿는 토큰 보유자는 다른 사람 ID로 접근 기록을 남길 수 있다. 전제를 문서에 못 박고(이미 PUBLIC_API E절에 있음) 서비스 포트가 게이트웨이 뒤에만 열리는지 deploy에서 확인.
- L5 보존 설정 [코드 읽기]: `_retention`은 빈 문자열(`SURVEY_SESSION_RETENTION_DAYS=`)도 ConfigError로 시작을 거부한다(이전엔 빈 값=끔). compose/deploy가 빈 값을 넣고 있으면 서비스가 뜨지 않는다. 또 끝난 세션이 90일 뒤 삭제되므로 결과 전달(dispatch)이 실패한 채 남은 세션도 삭제된다(추정, dispatch 재시도 상태와 연계 미확인).
- L6 문서·주석 불일치: `orchestrator.py`의 주석 "서비스는 설정 기본 8초를 준다"(실제 6초), `risk_rules.py` 모듈 docstring의 "기본 규칙 파일은 없다(설정이 없으면 비활성)"는 임시 기본 목록이 켜지는 현재 동작과 다름(파일 맨 위 docstring 갱신 누락). 기능 영향 없음.
- L7 401/403/429 거절마다 경고 로그 1줄(`api.py _record`): 토큰 없는 요청 폭주 시 로그 폭증. 비밀은 담지 않음을 확인(경로 이름과 상태만). 상한/샘플링은 선택. 연결 상한 503 응답(`process_request`)은 `pipeline_schema_version`과 `X-Request-Id`가 없다(클라이언트가 503을 상태 코드로 먼저 `UNAVAILABLE` 처리하므로 영향은 작다고 추정).

## 좋게 본 것 (확인)

- 비밀: 새 기기 토큰 표는 `read_secret`로 읽고 로그·오류에 값을 내지 않으며 `/readyz`에는 개수와 불리언만 나간다. 접근 기록·알림에는 발화 원문이 가지 않는다(evidence는 `signal:internal:<id>`).
- 알림 전달 실패 시 DELIVERY_FAILED가 프론트 신호로 나가고 세션 정지는 유지된다(재현 시험과 코드 일치). 확정 실패·마감 초과에서도 알림은 먼저 나간다.
- SSRF: 리다이렉트 비추적(`max_redirects=0`이 첫 3xx에서 예외로 끝남을 코드로 확인), 사설·링크 로컬·IPv4 매핑 IPv6 차단 확인.
