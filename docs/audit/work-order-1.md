# 작업 지시서 1 (2026-10-28, D104) — 영역 공통

근거: `structure-rules-audit-spec.md`(규칙 R1~R7), 영역별 점검 보고서(`docs/audit/structure-rules-2026-10-28.md`, 자기 리포).

## 이번 지시의 범위 (이것만 한다)
**A. 실제 계약 위반·데이터 손실·안전에 가까운 결함을 고친다.** 영역 지시에 적힌 항목만. 각 항목은
1. 먼저 결함을 재현하는 **실패하는 시험**을 쓴다(고치기 전에 실패를 눈으로 확인하고 출력을 기록한다).
2. 고친다. 시험이 통과함을 확인한다. 영역 전체 시험을 돌려 회귀가 없음을 확인한다.
3. 항목마다 따로 커밋한다.
재현이 되지 않으면(보고서의 서술이 틀렸으면) 고치지 말고 그렇게 보고한다.

**B. 영역 경계를 넘는 형식의 스키마 초안을 변경 요청으로 낸다 (코드는 아직 바꾸지 않는다).**
- 자기 점검 보고서의 "계약에 없는 경계 형식"(E절) 각각에 대해: 이 영역이 **받는** 형식이면 받는 것을, **내는** 형식이면 내는 것을 JSON Schema(2020-12)로 쓴다.
- 위치: `docs/change-requests/schemas/<이름>.schema.json`, 설명 문서는 `docs/change-requests/CR-<다음 번호>-boundary-schemas.md`.
- CR 문서에는 형식마다: 누가 만들고 누가 읽는가, 지금 실제 쓰는 유효한 예시 문서 1개 이상(실제 코드·설정에서 가져온다), 모르는 키 정책(거부/무시와 그 이유), 이 영역이 지키는 불변식.
- 초안은 반드시 `jsonschema`로 예시 문서에 대해 **실제로 검증**하고 그 명령과 출력을 CR에 적는다. 거부되어야 할 예시도 1개씩 둔다.
- 영역 코드가 이 스키마를 쓰도록 바꾸는 것은 헤드가 스키마를 계약에 올린 뒤의 다음 단계다. 지금 하지 않는다.
