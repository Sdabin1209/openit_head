# CR-H001 (초안): 직원 호출 전달 실패 뒤 재알림과 실패 기록

> **이 문서는 초안이다. 사용자 결정 전이며 확정된 것이 없다.** `boundary-contracts`는 수정하지 않았다(헤드가 소유하고, 이 초안은 사용자 결정 뒤에야 계약 변경으로 옮긴다). 아래 "제안"은 전부 제안이고, 값(간격·횟수)은 측정하지 않은 자리 표시다. "확인"이라고 적은 것은 이 초안을 쓰며 해당 문서를 읽고 확인한 것이다.
>
> 작성 2026-10-28, 헤드 문서 정리. 대장 항목: [`OPEN_GAPS.md`](../OPEN_GAPS.md) L23. 근거 점검: [`AUDIT_SUMMARY.md`](../AUDIT_SUMMARY.md) 3차 절.

## 1. 문제 (환자 안전)

위험 정지 또는 직원 호출 때 서버는 알림을 저장하고 직원 콘솔(SSE)과 웹 푸시로 보낸다. 전달 경로가 하나도 살아 있지 않으면 응답에 `staff_alert = DELIVERY_FAILED`가 실린다. 키오스크는 "현장 직원을 직접 부르는 화면"을 보여 주는 데서 멈춘다. **그 뒤 키오스크가 서버에 직원을 다시 부르라고 요청할 방법이 없고, "알림이 안 닿았다"는 사실을 서버 기록에 남길 방법도 없다.** 환자가 위험 신호로 멈춘 상태인데 직원이 오지 않으면, 키오스크와 서버 둘 다 이를 알 수 없다.

현재 키오스크가 하는 최선(확인): `DELIVERY_FAILED`면 세션을 끝내지 않고, '처음으로'를 누르면 "직원에게 직접 알리셨나요?"를 한 번 묻는다. 서버 세션이 "알림이 안 닿았다"는 유일한 흔적이라는 이유로 세션을 보존하는 것이다. kiosk-frontend `docs/design.md` 47행은 "알림을 다시 보내는 API는 계약에 없다(필요하면 변경 요청 사항)"이라고 적고 있다.

## 2. 현재 계약 (읽은 근거)

`boundary-contracts/HTTP.md`에는 직원 호출 관련 절이 없다(I1~I9 영역 사이 인터페이스만 있다. 확인). 직원 호출은 키오스크·직원용 공개 API인 `boundary-contracts/PUBLIC_API.md`에 있다.

- 34행, 응답 `FrontendInput.turn_failure_signal`: "`write_committed`(기록이 저장됐는지: COMMITTED/NOT_COMMITTED)와 `staff_alert`(직원 호출이 전달됐는지: NONE/DELIVERED/DELIVERY_FAILED)를 담는다. 프론트는 `DELIVERY_FAILED`이면 **현장 직원을 직접 부르는 화면**을 보여야 한다."
- 51행: "`TurnFailureSignal.staff_alert`: 알림이 저장되고 **전달 경로가 하나 이상 살아 있을 때**(SSE 연결 또는 푸시 서비스가 접수) `DELIVERED`, 아니면 `DELIVERY_FAILED`다. 저장된 알림은 `DELIVERY_FAILED`여도 목록에서 조회된다."
- 40~45행 직원 콘솔 표: 알림 목록(`GET /v1/staff/alerts`), 실시간 구독(`GET /v1/staff/alerts/stream`), 푸시 설정·구독 등록, 개입 결정(`POST /v1/sessions/{id}/intervention`). 모두 역할 `staff` 토큰 전용이다("키오스크 토큰은 403", 38행).
- 48행 `StaffAlert`: `alert_id`, `session_id`, `kind`, `created_at`, `status`(`OPEN`/`RESOLVED`), `resolved_by_decision`, `resolved_at`. 전달 시도나 실패를 나타내는 필드가 없다.
- 30행 `turn_id` 규칙: 같은 `turn_id` 재전송은 확정된 턴이면 같은 응답을 주고, 확정되지 못한 턴(`NOT_COMMITTED`)은 다시 처리한다. 위험 선별은 재전송에도 알림을 중복 만들지 않는다(알림은 세션·턴 기준 멱등). 즉 **발화를 다시 보내는 것은 재알림 수단이 아니다**(같은 알림이 멱등으로 흡수된다). 3차 점검은 "전달 실패 알림은 재시도 때 다시 전달"하도록 survey-service를 고쳤다고 적었으나(AUDIT_SUMMARY 3차 절), 이는 같은 `turn_id`를 다시 보낼 때만 일어나며 환자 발화 없이 키오스크가 시작할 수 없다. 이 서술은 요약 문서에서 읽은 것이고 survey-service 코드로 확인하지 못했다.
- 키오스크 토큰 역할이 호출할 수 있는 경로는 발화·종료 등이며, 알림 쪽 쓰기 경로는 직원·위험 감지기 역할에만 열려 있다(확인: 38행, 87행 `risk-source` 역할). 키오스크가 알림에 대해 할 수 있는 일은 없다.

## 3. 제안 (미결정)

세 가지를 모두 **덧붙이는** 방식으로 제안한다.

1. **재알림**: `POST /v1/sessions/{session_id}/staff-call/retry` (역할 키오스크, 그 세션을 만든 기기 토큰만).
   - 본문: 기존 `turn_id` 봉투 규칙을 따른다(같은 `turn_id` 재전송은 같은 응답). 별도 환자 발화·자유 문장 필드 없음.
   - 효과: 그 세션의 `OPEN` 알림을 **새로 만들지 않고 같은 `alert_id`로** 구독자(SSE, 웹 푸시)에게 다시 보낸다. `OPEN` 알림이 없으면 409.
   - 응답 200: `{"alert_id", "staff_alert": "DELIVERED|DELIVERY_FAILED", "delivery_attempts": n, "retry_after_s": s}`.
   - 서버가 호출 간격 하한을 둔다(너무 자주 누르면 429 + `Retry-After`). 간격·상한 값은 이 초안이 정하지 않는다(측정 없음, 현장 시험 필요).
2. **실패 기록**: `POST /v1/sessions/{session_id}/staff-call/report` (같은 키오스크 역할).
   - 본문: `{"outcome": "STAFF_NOTIFIED_MANUALLY" | "NOT_NOTIFIED", "turn_id": "..."}`. 키오스크의 "직원에게 직접 알리셨나요?" 응답을 서버에 남긴다.
   - 효과: 알림에 `manual_notice_reported_at`, `manual_notice_outcome`을 기록하고 감사 기록에 남긴다. 세션은 여전히 직원이 개입 결정으로 풀 때까지 `PAUSED_RISK`다.
3. **`StaffAlert` 선택 필드 추가**(모두 optional): `delivery_attempts`(정수), `last_delivery_status`(`DELIVERED|DELIVERY_FAILED`), `manual_notice_outcome`, `manual_notice_reported_at`. 직원 콘솔이 "전달 실패 알림"을 눈에 띄게 보일 수 있다.

미정(사용자·임상 확인 필요): 재알림 횟수 상한과 간격, `NOT_NOTIFIED`일 때 키오스크가 무엇을 하는지(계속 재알림? 환자 안내 문구?), 재전송 알림을 직원 콘솔이 같은 `alert_id`의 중복으로 합치는지(기존 콘솔의 중복 처리는 이 초안에서 확인하지 못했다. 합치지 않으면 새 이벤트 이름 `alert_retry`가 필요한데, 그러면 모르는 콘솔은 무시하므로 목적을 못 이룬다. 그래서 같은 `alert` 이벤트에 같은 `alert_id`를 권한다).

## 4. 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 지금처럼 키오스크가 "직접 알리셨나요?"만 묻고 서버에는 아무것도 남기지 않음 | 서버가 "안 닿았다"를 모르고, 직원 콘솔이 나중에 열려도 전달 실패를 구분할 수 없다. 환자 안전 경로가 키오스크 화면 상태에만 의존한다. 변경 비용은 0이지만 이 문제를 그대로 둔다 |
| 키오스크가 위험 감지기 경로(`POST .../risk-signals`)로 새 신호를 쏨 | 그 경로는 `risk-source` 역할 전용이고 새 알림을 만들며 세션 정지 의미가 있다(87~88행). 키오스크에 이 역할을 주면 권한 범위가 넓어지고, 재시도마다 알림이 중복된다 |
| 키오스크에 `GET /v1/staff/alerts`(읽기)를 열어 직원이 확인했는지 보게 함 | 직원 전용 목록이라 개인 단위 접근 제어 원칙(역할 분리, 38행)을 흐린다. 직원이 "확인했다"는 표시(ack) 개념도 지금 없다. 가치는 있어 후속 후보로 남기되 이 CR 범위에서는 뺀다 |
| 서버가 재시도 큐로 스스로 재전송 | 보완책이지 대체가 아니다. 살아 있는 구독자가 없으면 재전송해도 닿지 않고, 키오스크 쪽 "다시 부르기"를 환자·현장이 시작할 방법이 여전히 없다. 알림 DB 장애용 로컬 큐도 아직 없다(L14). 별도 후속 |
| 같은 `turn_id`로 발화를 다시 보내 재전달 유도 | 환자 발화 없이 못 하고, 위험 선별은 세션·턴 기준 멱등이라 새 알림이 생기지 않는다(30행). 의미를 발화 재전송에 얹는 것이라 규약을 흐린다 |
| 키오스크에 전화·호출 버튼 등 별도 하드웨어 경로 | 이 시스템의 범위 밖이고 현장 설비 결정이다. 이 CR은 소프트웨어 경로의 빈칸만 다룬다 |

## 5. 하위 호환

- 새 엔드포인트 두 개와 `StaffAlert`의 optional 필드만 더한다. 기존 요청·응답의 의미를 바꾸지 않는다. 읽기 모드 검증은 같은 MAJOR의 모르는 필드를 받아들이므로(HTTP.md 공통 절, 확인) 새 필드를 모르는 기존 직원 콘솔·클라이언트가 깨지지 않는다.
- 계약 버전은 호환 가능한 추가이므로 MINOR 후보다. 정확한 번호와 `CONVENTIONS.md`의 규칙 적용은 헤드가 확정한다(이 초안은 그 문서의 버전 규칙을 다시 읽지 않았다).
- 새 키오스크 + 옛 서버: 새 엔드포인트가 404/405다. 키오스크는 기능 감지로 현재 동작("직접 알리셨나요?")으로 물러나야 한다. 옛 키오스크 + 새 서버: 새 엔드포인트를 쓰지 않을 뿐이다. 배포 순서는 survey-service 먼저, 키오스크 나중이다.
- 문진 스키마(정수 버전 1)에는 손대지 않는 안이다. `TurnFailureSignal`은 그대로 둔다. `StaffAlert`의 위치는 이 초안에서 `boundary-contracts/schemas`로 확인했다(`StaffAlert.schema.json`). `survey-service/schema` 쪽 변경이 필요한지는 확인하지 못했다.

## 7. 사용자 결정이 필요한 것

1. 이 방향(재알림 + 실패 기록, 덧붙이기)으로 계약 변경을 진행할지.
2. 임상 현장 흐름: 직원이 오지 않을 때 환자·현장에서 실제로 무엇을 하는지(재알림 상한과 간격, `NOT_NOTIFIED` 뒤 동작).
3. 직원이 확인했다는 표시(ack)와 키오스크의 읽기 권한을 같이 다룰지, 후속으로 미룰지.

결정이 나면 헤드가 `boundary-contracts`에 반영하고(PUBLIC_API.md, `StaffAlert` 스키마, 예시·적합성 시험, CHANGELOG, 태그), 영역에 지시한다. 그 전에는 L23이 열려 있다.
