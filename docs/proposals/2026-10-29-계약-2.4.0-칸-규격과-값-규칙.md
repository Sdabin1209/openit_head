# 계약 2.4.0 초안: LoRA-A가 칸 규격과 값 규칙을 보증한다 (U32·U33·U24)

- 상태: **초안(릴리스 안 함)**. 2026-10-29 헤드. 구현 전에 이 초안으로 영향 영역과 순서를 맞춘다.
- 관련: ADR 0010(LoRA-A 출력 규칙은 데이터, 서버가 보증), R7(컴포넌트가 낸 값은 받는 쪽이 다시 검증하지 않음), D74(서비스를 데이터셋 v2에 맞춤), OPEN_GAPS U24·U32·U33.

## 문제

- 데이터셋 v2의 정답은 정규화기가 칸 규격(학습 서버 `~/WS/dataset/docs/SQL.md` 5.2 `question_fields`: 자료형, `constraints_json`)과 교차 규칙(R1~R3)으로 만들었다. 모델은 이 규격을 입력으로 받지 않고 정답 예시로만 배운다.
- 모델은 이 규칙을 틀린다(학습 서버 `~/taehyeon/runs/a_*_v2/analysis_test.txt`). 데이터셋 쪽 DB는 트리거로 범위 밖 값을 막았지만, 우리 시스템에는 그 안전망이 없다.
- 지금 우리 쪽 검사는 둘로 나뉘어 있다. model-runtime `check_action_extraction`은 흐름 표만 알고, survey-service에 문항 세트 검사 4개와 재호출이 남아 있다(U24, R7 위반).

## 결정안

1. **칸 규격을 계약 모양으로 정의한다.** 새 스키마 `QuestionFieldSpec`을 둔다.
   - 칸마다 `slot`(문항.칸, 예 `Q10.days`), `data_type`(`boolean`·`integer`·`number`·`option`), 선택 `minimum`·`maximum`·`exclusive_minimum`, 선택지 칸이면 `options`(코드 목록), 반복 키 칸이면 `repeat_keys`(예: soju, beer, spirits, makgeolli, wine)를 적는다.
   - 값은 데이터셋 `question_fields`·`field_options`와 같아야 한다.
2. **I9 요청에 칸 규격을 싣는다.** `ExtractRequest`에 선택 필드 `fields`(QuestionFieldSpec)를 더한다.
   - 2.x에서는 선택이다. `fields`가 있으면 서버가 아래 3·4를 보증한다. 3.0.0에서 필수로 만든다.
   - `fields`의 출처는 survey-service 문항 스키마의 칸 정의다. 그 칸 정의에 자료형·최소·최대를 더한다(survey-schema 1.2.0, survey-service 소유). question-authoring 작성 양식도 그 칸을 읽는다.
3. **자료형·범위 검사와 출력 바꾸기(U32).** 규칙 데이터 `ActionExtractionRules`에 `value_range` 블록을 더한다. 출력의 칸 값이 자료형이 다르거나 범위 밖이면, 그 칸을 데이터셋 정답 모양으로 바꾼다. 실제 데이터셋 예(Q10 "여덟 일")는 이렇다.
   - `value: null`, `status: UNCLEAR`, `save: false`, `precision: unspecified`
   - `action: REASK`, `reason: OUT_OF_RANGE`, `targets: [그 칸]`, `next_item: 그 칸의 문항`
4. **교차 규칙(U33).** 규칙 데이터에 블록 세 개를 더한다. 바꾼 출력 모양은 데이터셋 정답에서 확인했다.
   - **R2 `count_exceeds_days`:** `Q7.frequency`가 `Q7.unit`의 기간 일수(week 7, month 31, year 366, 정규화기 `PERIOD_MAX`)를 넘으면 두 칸을 위 3의 모양으로 만든다. `REASK / COUNT_EXCEEDS_DAYS`, `targets: [Q7.frequency, Q7.unit]`. 같은 출력의 `Q7.does_not_drink=false`는 저장 그대로 둔다(데이터셋 예와 같음).
   - **R3 `max_below_usual`:** 같은 술 종류에서 `Q7_2`(최대)의 mL가 `Q7_1`(평소, 상태 값)의 mL보다 작으면 `CONFIRM / CONFLICT_MAX_BELOW_USUAL`로 바꾼다. 이번 `Q7_2[종류].amount·unit`은 값을 유지하되 `status: CONFLICT`, `save: false`, `targets`는 그 두 칸, `next_item: Q7_2`. 술 종류×단위의 mL 환산표를 규칙 데이터에 둔다. 값은 정규화기 `mappings.py` `volume_ml`에서 옮기며, 아직 옮겨 적지 않았다(미확인).
   - **R1 `does_not_drink_with_frequency`:** 데이터셋 정답에 이 충돌은 0건이다. 정규화기는 횟수가 있으면 `does_not_drink`를 false로 고쳐 저장한다. 출력 값을 고치는 유일한 규칙이므로 구현 전에 헤드가 정규화기 동작을 다시 확인한다.
5. **검사 범위는 데이터셋이 정답을 가진 경우로 한정한다.** `OUT_OF_RANGE`(days, use_pattern, duration_minutes), `COUNT_EXCEEDS_DAYS`, `CONFLICT_MAX_BELOW_USUAL`이다. 데이터셋에 정답이 없는 위반(예: 음수 개비 수)은 바꾸지 않고 지금처럼 출력 거부(`OUTPUT_INVALID`)로 처리한다. 바꿔 내면 LoRA-B가 학습하지 않은 일반 문장이 나가기 때문이다.
6. **survey-service는 중복 검사 4개와 재호출을 지운다(U24).** 서버가 보증한 출력을 믿는다(R7).

## 바뀌지 않는 것

- 출력 스키마 `ActionExtraction`, LoRA-B 입력 `ResponseRequest`와 문장표, 키오스크, 배포 구조, 모델 학습

## 한계

- 선택지 칸(Q6_1 '32일' → `days_10_29`)은 원래 숫자가 출력에 없어서 잡지 못한다.
- 범위 안이면서 틀린 값(그럴듯한 오답)도 잡지 못한다.
- "모델이 틀렸을 때 데이터셋 정답 모양으로 바꾸는 것이 옳은가"는 데이터셋으로 검증된 적이 없다. 정답을 만든 규칙과 같다는 것이 근거다. 실제 모델에 적용한 효과는 GPU 평가로 확인한다.

## 열린 질문

- R1 처리(값을 고치는 규칙)를 둘지: 정규화기 동작을 다시 확인한 뒤 정한다.
- mL 환산표 값: 정규화기 `volume_ml`과 데이터셋 정답 606건이 같은 표에서 나왔는지 확인한다.
