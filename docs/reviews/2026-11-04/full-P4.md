## 계약 문장을 고쳐야 하는 것 (계약 빈칸 8칸, 모순 1칸 = 6건)

1. **R3.10 끝에 접속 대기 기본값** (칸 C24 F03·F07). 위치: RUNTIME R3.10 입력 칸 끝. 문장: "데이터베이스를 가진 서비스 중 Env 에 `*_DB_CONNECT_TIMEOUT_SECONDS` 가 없는 서비스는 접속 대기를 R10.3 의 10초(시작값·측정 안 함)를 넘기지 않는다." 근거: R3.10 이 인용한 키가 GateEnv·QuestionAuthoringEnv·SurveyServiceEnv 에만 있다(OpsFeedbackServerEnv·DatasetStoreEnv·ModelRegistryEnv 에는 DB 키 없음, 스키마 확인함). R10.3(표에 없는 호출의 소켓 단위 10초)의 일반화.
2. **R3.18 푸시 시간 한도 값** (칸 C23 F03). 위치: R3.18 "시간 한도 안에서 끝낸다" 뒤. 문장: "푸시 한 건의 대기 한도는 `SurveyServiceEnv.SURVEY_PUSH_TIMEOUT_SECONDS`(기본 3.0초·측정 안 함)이고 턴 총 마감 50초 안쪽이다." 근거: CONVENTIONS 시간 상한 사슬(안쪽 < 바깥), D89.
3. **R3.18 재전송 한도와 구현 불일치** (칸 C23 F02·F07). 위치: R3.18. 권장 문장: "429·5xx → 그 시도는 `DELIVERY_FAILED` 로 기록하고 자동으로 다시 보내지 않는다. 같은 알림의 재전송은 직원 호출 재알림(PUBLIC_API G절)이 같은 `alert_id` 로 하며 `Topic` 헤더로 미전달 이전 메시지를 대체한다(RFC 8030 5.4)." 근거: 읽은 survey-service `link_push.py` 는 한 번만 보내고 `Retry-After` 재전송이 없다(읽은 범위 한정, 다른 파일에 있을 수 있음). 현행 R3.18 의 "Retry-After 를 따라 다시 보낸다"는 횟수·시간 한도가 없어 구현할 수 없는 문장이다. 대안: 계약을 유지하고 "푸시 `TTL` 3600초(RFC 8030 5.2) 안에서 알림당 최대 3회(시작값·측정 안 함)"로 상한을 적고 survey-service 가 구현.
4. **CONVENTIONS 13절 예외에 OUT-FILE** (칸 C36 F04, 같은 사유가 C36 전체). 위치: 13절 "유일한 예외: 배포 때의 환경 설정" 목록. 문장: "compose 밖 호출자에게 주는 루트 인증서 PEM·hosts 표·두 파일의 SHA-256 목록(RUNTIME R1.5, OUT-FILE)". 근거: R1.5 가 출력하는 쪽을 deploy(배치 도구)로 정하는데 13절 예외 목록에 없어, 영역 게이트웨이를 지나지 않는 deploy 출력이 목록 밖에 있다.
5. **R10.1 의 감시 실패 포인터** (칸 C30 F04·F05). 위치: R10.1 끝 문장. 현행: "감시 수집은 그 영역 게이트웨이를 지나 R1.1~R1.3 대로 TLS·검증, 실패는 R10.11". R10.11 에는 실패 출력이 없다. 바꿀 문장: "감시 수집의 실패(연결 실패·5xx)는 감시(platform)가 받는 것이고 처리는 platform 소관이다; 영역 서비스의 출력은 R3 의 해당 행과 R10.11 이다." 근거: 구조 규칙 4(컴포넌트는 자기 입출력만 안다).
6. **모순: R9.3 대 JobsDeclaration 설명** (칸 C33 F03). 두 문장: R9.3 "deploy 는 3600초(시작값, 측정 안 함 …)를 상한으로 쓴다" / `schemas/JobsDeclaration.schema.json` job.timeout_seconds "없으면 deploy 의 기본 상한(deploy ADR)을 쓴다". 고칠 쪽: 스키마 설명. 바꿀 문장: "없으면 RUNTIME R9.3 의 3600초(시작값·측정 안 함)를 쓴다 — 선택 필드인 이유: 기존 선언과 하위 호환(CONVENTIONS 1절 3)." (스키마 설명을 바꾸면 3.4.4 문서/스키마 일관성 시험 확인 필요 — 시험은 돌리지 않았다.)

## 확인한 것과 못 한 것
- 확인한 것: 210칸을 모두 현행 조항과 대조했다. 클라이언트 출력은 `_http.py` 의 상태 → code 매핑(5xx·비 BoundaryError 503 → `UNAVAILABLE`, 소켓 timeout → `UNAVAILABLE`)과 맞는지 보았다. FrontendInput 스키마가 R3.20 의 `response_text=null`·`turn_failure_signal` 을 허용함을 확인했다.
- 하지 못한 것: 시험(`verify.py`, tests)은 돌리지 않았다. 구현 대조는 survey-service 푸시 코드 한 곳만 읽었다. HTTP.md I1~I8 절과 다른 영역 구현은 읽지 않았다. 클라이언트가 tar 호출에서 timeout 300초를 실제로 넘기는지는 호출 영역 코드를 보지 않았다(R10.3 은 호출자가 넘긴다고 정함).
