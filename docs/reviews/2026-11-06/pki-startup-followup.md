# 10:13 기동 실패 뒤 추가 검토

검토 기준: deploy `14ddfba`, boundary-contracts `2368f83`(3.4.20), link `3311776`(0.4.25). 수정된 영역 작업 트리의 HEAD를 확인했다. E2E 전체 재실행 결과를 주장하는 문서가 아니다.

## 확인한 추가 결함과 수정

1. **인증서 이름도 외부 호스트를 거부했다.** 토큰 발급 이름만 넓히면 `compose.inference.yaml`의 `STEP_CERT_NAME=host.docker.internal`이 다음 단계에서 다시 거부된다. 수정 전 계약 검증기로 token·cert 두 역할의 pattern 위반을 각각 확인했다. `StepCaEnv`의 두 속성이 공통 DNS 이름 정의를 따르게 수정했다. label/전체 길이·목록 구분자·개행·잘못된 이름도 검사한다. 계약은 `v3.4.21`이다.
2. **토큰 복사 실패를 성공으로 반환했다.** `cp ...; rm -rf ...`에서 마지막 정리 명령이 실패 상태를 가렸다. 없는 출력 부모 경로로 호출하는 회귀 시험은 수정 전 실패했다. 이제 게시 실패를 반환한다.
3. **토큰 발급 컨테이너에 비밀 파일 그룹이 없었다.** 비밀은 0640 + SECRETS_GID인데 직접 `docker run`에는 group-add가 없었다. 호스트와 이미지 UID가 다르면 읽기를 보장하지 못한다. 입력 비밀 그룹을 전달하고 출력도 0640 + 같은 그룹으로 게시한다. 이미지 UID를 배포 코드에 적지 않는다.
4. **E2E가 토큰을 0644로 바꿨다.** `issue_tls_token`은 공개 루트 인증서와 비밀 OTT를 함께 chmod했다. 실제 함수 원문을 가짜 Docker와 실행하는 시험이 수정 전 실패했다. 공개 인증서만 0644로 하고 OTT는 위 게시 규칙을 유지한다.

추가로 `step_issue_token`은 실제로 Docker에 넘길 환경 배열 하나를 먼저 `StepCaEnv`로 검증한다. 검증용 값과 실행용 값을 따로 만들지 않는다. 스키마 위반이면 Docker를 실행하지 않는 것도 시험했다.

## 기동 전 검사 자체의 누락 추가 확인

실제 10:14 진단 파일(`deploy/state/e2e-diag-20261106-101409/chk-…3650.txt`)은 StepCaEnv.STEP_TOKEN_NAMES의 pattern 거부를 기록한다. 당시 빌드 기록과 step-ca 이미지 라벨도 계약 v3.4.20이다. 소스의 v3.4.21 수정이 그 기존 이미지에 반영됐다고 간주할 수 없다.

별도로 기동 전 검사에서 CommonEnv가 적용되지 않는 것을 재현했다. Compose 문서의 survey-service에 `OPENIT_EGRESS_PROXY=http://outside.invalid:3128`을 넣고 검증기만 호출하면 수정 전에는 rc=0이었다. 컨테이너나 네트워크 호출은 실행하지 않았다. 서비스 Env는 자기 접두사만 제한하므로 이 공통 값은 서비스 Env를 통과하고, 소비 SDK의 require_egress_proxy에서야 거부된다. 검사 문서 목록을 만드는 코드가 공통 계약 문서를 빠뜨린 것이 원인이다.

deploy `a90f4d6`에서 모든 서비스·잡의 실제 환경에 CommonEnv 검증을 추가했다. 서비스 출구 URL, 잡의 백업 URL, 잡 비밀 파일의 상대 경로를 거부하는 시험을 추가했다. 설정 관문 12개, deploy 구조 10개, 설정 파일 4개 시험이 통과했다. 전체 E2E는 실행하지 않았다.
